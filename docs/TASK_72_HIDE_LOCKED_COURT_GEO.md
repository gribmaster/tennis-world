# TASK 72 — Locked courts have no map position for viewers without membership

**Model: Sonnet 5, reasoning effort: high.** Security-relevant and cross-cutting (contracts, API, web). Read `docs/TASK_25_*.md`, `docs/TASK_26_*.md` and the headers of `apps/api/src/courts/courts.mapper.ts`, `components/court/court-display.ts`, `features/map/map-markers.ts` first. Do the work in the order **A → B → C → D** and do not start a later part until the earlier part's checks pass.

## Goal

Today a premium (`isLocked`) court is hidden from non-members only *cosmetically*: the UI shows "Premium Court" and a lock, **but the API sends every viewer the court's approximate coordinates (`approxLat`/`approxLng`, ±~10 km) and the web plots a pin from them** — so anyone can read the rough position of every premium court from the map or from the network response.

New rule (owner decision): **for a locked court, a viewer who is not entitled (guest or free account) gets no map point and no approximate location at all** — not hidden by CSS, not blurred, but *not sent*. Entitled viewers see exactly what they see today.

## Decisions already made (do not re-litigate)

1. **Who is "not entitled":** anyone for whom `EntitlementsService.isEntitled(userId)` is false, plus every anonymous request. That service is the single gate (`DEV_FORCE_MEMBERSHIP` therefore applies automatically; do not read that variable anywhere new).
2. **What is removed:** for `court.isLocked && !viewerEntitled`, the keys **`approxLat` and `approxLng` are omitted** from the JSON (the keys are absent — not `null`, not `0`, not a coarser value). Unlocked courts keep them for everyone. Entitled viewers keep them for everyone. The exact-location path (`/v1/me/courts/:slug/exact-location`) is untouched. `mapCoords` (the legacy stylized-canvas `[x%, y%]`, documented as "NEVER geographic") is left alone — but check in step A whether anything still renders it as a position; if it does, report it, don't fix it here.
3. **Where it is enforced:** on the **API**, in one function (`redactCourtGeo(dto, viewerEntitled)` next to the court mapper) that **every producer** of `CourtSummaryDTO` / `CourtDTO` goes through. Find them all — at least `courts.service` (`list`, `getBySlug`, `getRelated`, search if present), `me/saved-courts.service`, `me/collections.mapper`/service (folder courts and covers), and any other endpoint the grep finds (the public `collections` module only returns member *counts* today, so it should not need redaction — confirm that rather than assume it). Prove completeness with a grep for `courtSummarySelect`, `courtDetailSelect`, `toCourtSummaryDTO`, `toCourtDTO` (a new producer must not be able to skip redaction: prefer making the mapper take the viewer flag as a required argument over a post-processing step callers can forget). **The web additionally never plots/prints such a court even if it receives coordinates** (defence in depth; also what makes `mock` data-source mode behave).
4. **`GET /v1/courts/map` (pins):** for a non-entitled viewer, locked courts are **excluded from the response entirely** (a pin with no position has no meaning). Entitled: unchanged.
5. **Viewer resolution on public endpoints must never turn a public endpoint into a protected one.** Add an optional-viewer step for the public court (and public collections) routes that behaves like `AuthGuard`'s token extraction (cookie first, then Bearer, and the staging demo-auth header branch) but **never throws**: no/invalid/expired token ⇒ anonymous ⇒ redacted, HTTP 200. Reuse `AuthGuard`'s extraction logic through a shared helper rather than copying it; `AuthGuard`'s own behaviour must not change (`verify:api-auth`, `verify:staging-demo-auth`, `verify:google-oauth` stay green).
6. **Caching:** these responses now depend on the viewer. Set `Cache-Control: private, no-store` and `Vary: Cookie, Authorization` on the affected public endpoints so no CDN/shared cache can serve a member's response to a guest. (The web's server-side fetches already use `cache: 'no-store'`; keep it.)
7. **Contract:** in `packages/contracts/src/court.ts`, `approxLat` / `approxLng` become **optional** on `CourtSummary` and `Court` (update the file's header comment: approximate coordinates are present only for unlocked courts or entitled viewers). This is a deliberate breaking change for any consumer that assumed they are always present (the mobile app is such a consumer — say so in the report). Do not change `MapPin` shape other than the exclusion in decision 4.
8. **No schema change, no seed/import change, no new dependency.** The DB columns stay (entitled viewers need them).
9. **Out of scope — report, don't change:** the court's `name`, `country` and `region` strings are still sent to everyone and only masked in the UI (Task 25's design). They are also location information. Do **not** redact them here; list it under "Needs a decision" in the report with the places they flow through, so the owner can decide whether the API should redact them for non-entitled viewers too.

## Part B — Web data plumbing

Public pages that need coordinates must now fetch courts **as the viewer**, otherwise members would lose their pins:
1. The public court/collection repository reads (`http-court.repository.ts` etc.) currently ignore the cookie ("the public discovery repos ignore it" — see `getRepositoriesForRequest`). For request-scoped server callers, forward the incoming cookie (and the demo-auth options) to these reads too. Do it in the existing request-scoped factory (`lib/repositories.server.ts`), don't invent a second one. Pages to switch from the cookie-less `repositories.courts…` to the request-scoped set **only where coordinates are used**: `/map`, `/courts/[slug]`, `/saved` (wishlist map) and `/saved/collections/[slug]`, plus any other page found by the grep in step C1. Pages that never read coordinates stay as they are.
2. The guest path must keep working: a missing cookie is not an error on these public reads; `AuthRequiredError` is still only for protected reads.
